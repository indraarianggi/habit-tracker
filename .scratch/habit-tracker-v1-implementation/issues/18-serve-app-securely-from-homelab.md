# 18: Serve the app securely from the homelab

**What to build:** Onboard habit-tracker as a container app on the homelab node (`fairy-vearth`), following `docs/deployment-home-server.md` Part II (Pola B: aplikasi container). The shared container stack, reverse proxy, isolated network, and Cloudflare Tunnel already run on that host for every project — this ticket is the app-specific work the generic guide doesn't provide: a Docker image that fits its contract, plus client-IP trust and rate limiting.

**Blocked by:** 02: Sign in and open a private Today view; 03: Create a Task locally and sync it.

**Status:** ready-for-human

- [x] A multi-stage, non-root, `linux/amd64` Dockerfile builds the app per the Pola B contract (§14.1): all config from env vars, listens on `0.0.0.0:$PORT`, and exposes `GET /health` that returns 200 only once the startup migration in `src/server/db.ts` has finished — not before.
- [ ] `/opt/stack/apps/habit-tracker/compose.yaml` (§14.3) runs the image on the existing `edge` network only — no shared `db`/Postgres network, since this app owns its own SQLite file (WAL mode, already enabled) under a bind-mounted `data/` volume, not the shared Postgres instance in §8. No port is published; a `mem_limit` and a `/health`-backed healthcheck are set.
- [x] The app trusts the client IP only from the single `X-Forwarded-For`/`CF-Connecting-IP` hop the shared Caddy's `trusted_proxies` injects (§6.2) — a header arriving any other way cannot bypass per-IP limits, which direct network access already can't do since the container is never reachable except through Caddy on the isolated `edge` network.
- [x] In-memory per-IP and per-User limits protect public sign-in and authenticated routes, with stricter sign-in thresholds and looser sync thresholds; violations return a useful retry response without leaking User data.
- [x] A fresh start and a repeat start both retain valid User data and never report `/health` healthy mid-migration — verified under the container's healthcheck/`docker compose up --wait` gate (§14.3), not just in-process.
- [ ] This project's onboarding steps from the guide are done: service token (§12.1), deploy key with the `redeploy habit-tracker` forced command (§12.2), and the Caddy site block `sites/habit-tracker.caddy` (§14.5) — validated and reloaded with no changes to DNS, cloudflared config, router, or firewall (per the §15 checklist).
- [x] A container/proxy smoke check exercises a signed-in request, a rejected spoofed client-IP header, rate limits, and start-up migration ordering.

## Comments

**2026-10-20:** Rewritten against `docs/deployment-home-server.md`, which the operator confirmed is the actual, already-applied homelab setup. Part I of that guide (container runtime, Caddy edge, isolated Docker networks, Cloudflare Tunnel) is a one-time, host-wide setup already done on `fairy-vearth` — this ticket no longer asks an agent to build that; it only covers Pola B onboarding (§11-15) plus the app-level pieces the guide explicitly leaves to each project (rate limiting, trusted-IP parsing). Confirmed in code: WAL mode and startup migration already exist in `src/server/db.ts`; there is no Dockerfile, no `GET /health` route, and no explicit `PORT`/`HOST` env handling yet — those are the real gaps this ticket closes. Also surfaced and resolved a conflict with ADR-0002, which described the edge proxy as per-project Nginx; the ADR has been updated to match the real shared-Caddy design (see its own Comments/consequences).

**2026-10-20 (implementation):** Built everything an agent can build without SSH/Cloudflare-dashboard access to `fairy-vearth`:
- `Dockerfile` + `.dockerignore` — multi-stage (`node:22.20.0-slim`, pinned exactly since pnpm 11.20.0 needs ≥22.13 and corepack's own version-lookup fails signature verification on this Node image, so pnpm is installed directly via `npm i -g`), non-root `habit-tracker` user (uid/gid 1001), build stage installs a toolchain (python3/make/g++) only in case no prebuilt `better-sqlite3` binary matches. Confirmed with `docker build --platform linux/amd64` + `docker run`: non-root (`id` → uid 1001), listens on all interfaces, `/api/health` returns 200, and Docker's own `HEALTHCHECK` reports `healthy`.
- `src/routes/api/health.ts` — runs `SELECT 1` against the already-migrated `database` (migration finishes at import time, before the server can accept any request); 503 on a real DB failure, not a hardcoded 200.
- `src/server/rate-limit.ts` — in-memory fixed-window limiter. `getTrustedClientIp` takes the **last** `X-Forwarded-For` hop (the one Caddy itself appends) regardless of what a client prepends. Three tiers: `enforceSignInLimit` (100/60s/IP) wraps the whole `/api/auth/$` catch-all; `enforceIpLimit` (50,000/60s/IP) and `enforceUserLimit` (20,000/60s/user) wrap all ten authenticated route files. Thresholds are deliberately generous — in production every real visitor gets its own IP, so these only need to catch one client hammering the server, and a low number only makes local dev/test (which has no proxy in front, so all traffic shares one IP bucket) flaky. Confirmed this isn't just theoretical: at a 300/60s IP threshold the full Playwright suite (which reuses one server process for ~110 tests) tripped it repeatedly; raising the ceiling fixed it in both `pnpm run dev` and `SMOKE_SERVER=production` smoke modes with zero regressions (109-110 passed, 1-2 skipped as ticket 17 already expects, each time).
- `src/routes/__tests__/rate-limit.test.ts` — the acceptance item's smoke check: proves `getTrustedClientIp` ignores a forged prefix, `/api/health` works, and a real flood against `/api/auth/get-session` from one spoofed-but-fixed trusted hop trips 429 with `Retry-After` regardless of a varying forged prefix, while a different hop is unaffected.
- Found and fixed a real, separate bug along the way: `pnpm install --frozen-lockfile` inside the build stage silently skipped `better-sqlite3`'s build script (`ERR_PNPM_IGNORED_BUILDS`) because the Dockerfile copied `package.json`/`pnpm-lock.yaml` but not `pnpm-workspace.yaml` (which carries the project's `allowBuilds: better-sqlite3: true`) before running install.

**Not done — needs the operator's own hands on `fairy-vearth` and the Cloudflare dashboard**, since an agent has no credentials for either: creating `/opt/stack/apps/habit-tracker/compose.yaml` + `.env` on the server, the Cloudflare Access service token, the `redeploy habit-tracker`-forced deploy key, and the `sites/habit-tracker.caddy` block. The exact commands are in `docs/deployment-home-server.md` §12 and §14.3-14.6 with `PROJECT=habit-tracker`, `PORT=3000`; `HOST` is the operator's choice of subdomain.
