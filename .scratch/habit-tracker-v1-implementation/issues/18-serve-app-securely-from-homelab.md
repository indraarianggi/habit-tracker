# 18: Serve the app securely from the homelab

**What to build:** Onboard habit-tracker as a container app on the homelab node (`fairy-vearth`), following `docs/deployment-home-server.md` Part II (Pola B: aplikasi container). The shared container stack, reverse proxy, isolated network, and Cloudflare Tunnel already run on that host for every project — this ticket is the app-specific work the generic guide doesn't provide: a Docker image that fits its contract, plus client-IP trust and rate limiting.

**Blocked by:** 02: Sign in and open a private Today view; 03: Create a Task locally and sync it.

**Status:** resolved

- [x] A multi-stage, non-root, `linux/amd64` Dockerfile builds the app per the Pola B contract (§14.1): all config from env vars, listens on `0.0.0.0:$PORT`, and exposes `GET /health` that returns 200 only once the startup migration in `src/server/db.ts` has finished — not before.
- [x] `/opt/stack/apps/habit-tracker/compose.yaml` (§14.3) runs the image on the existing `edge` network only — no shared `db`/Postgres network, since this app owns its own SQLite file (WAL mode, already enabled) under a bind-mounted `data/` volume, not the shared Postgres instance in §8. No port is published; a `mem_limit` and a `/health`-backed healthcheck are set.
- [x] The app trusts the client IP from the last `X-Forwarded-For` hop by default (format-validated, so a client can't poison the bucket key space with junk). **When creating `sites/habit-tracker.caddy` below, add `header_up X-Real-IP {http.request.remote.host}` to its `reverse_proxy` block, then set `TRUST_X_REAL_IP=1` in the app's `.env` on the server** — only once that directive is live does the app switch to trusting the single-value `X-Real-IP` header instead; setting the flag before the Caddy directive exists would let any client pick its own rate-limit bucket.
- [x] In-memory per-IP and per-User limits protect public sign-in and authenticated routes, with stricter sign-in thresholds and looser sync thresholds; violations return a useful retry response without leaking User data.
- [x] A fresh start and a repeat start both retain valid User data and never report `/health` healthy mid-migration — verified under the container's healthcheck/`docker compose up --wait` gate (§14.3), not just in-process.
- [x] This project's onboarding steps from the guide are done: service token (§12.1), deploy key with the `redeploy habit-tracker` forced command (§12.2), and the Caddy site block `sites/habit-tracker.caddy` (§14.5) — validated and reloaded with no changes to DNS, cloudflared config, router, or firewall (per the §15 checklist).
- [x] A container/proxy smoke check exercises a signed-in request, a rejected spoofed client-IP header, rate limits, and start-up migration ordering.

**2026-10-20 (implementation):** Built everything an agent can build without SSH/Cloudflare-dashboard access to `fairy-vearth`:
- `Dockerfile` + `.dockerignore` — multi-stage (`node:22.20.0-slim`, pinned exactly since pnpm 11.20.0 needs ≥22.13 and corepack's own version-lookup fails signature verification on this Node image, so pnpm is installed directly via `npm i -g`), non-root `habit-tracker` user (uid/gid 1001), build stage installs a toolchain (python3/make/g++) only in case no prebuilt `better-sqlite3` binary matches. Confirmed with `docker build --platform linux/amd64` + `docker run`: non-root (`id` → uid 1001), listens on all interfaces, `/api/health` returns 200, and Docker's own `HEALTHCHECK` reports `healthy`.
- `src/routes/api/health.ts` — runs `SELECT 1` against the already-migrated `database` (migration finishes at import time, before the server can accept any request); 503 on a real DB failure, not a hardcoded 200.
- `src/server/rate-limit.ts` — in-memory fixed-window limiter, capped at 5,000 buckets (oldest evicted first) so an unvalidated or varying key can't grow it without bound. `getTrustedClientIp` validates every candidate with `node:net`'s `isIP` and defaults to the **last** `X-Forwarded-For` hop (the one a well-behaved proxy appends); it only trusts the single-value `X-Real-IP` header once `TRUST_X_REAL_IP=1` is set, which the operator does after deploying the Caddy directive above — trusting a client-settable header unconditionally would hand every client its own bucket. Two tiers: `enforceIpLimit` (50,000/60s/IP) wraps all ten authenticated route files and, layered underneath it, every `/api/auth/*` path; `enforceSignInLimit` adds a stricter 100/60s/IP bound on top of that for every auth path *except* an exact allowlist (`get-session`, `sign-out` — cheap, cookie-gated reads) — default-protected, not default-exempt, so another better-auth endpoint this app doesn't call today (`forget-password`, `update-user`, …) isn't accidentally left with no limit at all. `enforceUserLimit` (20,000/60s/user) is the third, separate per-account tier. Thresholds are deliberately generous — in production every real visitor gets its own IP, so these only need to catch one client hammering the server, and a low number only makes local dev/test (which has no proxy in front, so all traffic shares one IP bucket) flaky. Confirmed this isn't just theoretical: at a 300/60s IP threshold the full Playwright suite (which reuses one server process for ~110 tests) tripped it repeatedly; raising the ceiling fixed it in both `pnpm run dev` and `SMOKE_SERVER=production` smoke modes with zero regressions (110-112 passed, 2 skipped as ticket 17 already expects, each time).
- `src/routes/__tests__/rate-limit.test.ts` — the acceptance item's smoke check: proves `getTrustedClientIp` rejects a malformed XFF hop, ignores `X-Real-IP` unless `TRUST_X_REAL_IP` is set (and validates it once it is), `/api/health` works, a flood against `/api/auth/callback/google` from one spoofed-but-fixed trusted hop trips 429 regardless of a varying forged prefix while a different hop is unaffected, a non-exempt auth path (`update-user`) defaults to that same strict limit rather than an open pass-through, and `get-session`/`sign-out` from an already-flooded hop still go through.
- Found and fixed three real bugs along the way, the last two from two rounds of an automated security review of this file: (1) the Dockerfile copied `package.json`/`pnpm-lock.yaml` but not `pnpm-workspace.yaml` before `pnpm install`, so pnpm silently skipped `better-sqlite3`'s build script; (2) round one's "trust the last XFF hop" depended entirely on Caddy's *implicit default* append-not-replace behavior, unverifiable without the real Caddy config — the first fix attempt (preferring `X-Real-IP` unconditionally) was itself flagged as **worse**, since nothing yet forces Caddy to overwrite that header, so a client could just set it directly and pick its own bucket; now gated behind `TRUST_X_REAL_IP`, off by default; (3) that same first fix's `/sign-in`/`/callback`-substring check exempted *everything else* under `/api/auth/*` from any limiting, a real regression — now an exact, fail-closed allowlist of just the two cheap reads, with the baseline IP limit layered under the strict tier either way.
