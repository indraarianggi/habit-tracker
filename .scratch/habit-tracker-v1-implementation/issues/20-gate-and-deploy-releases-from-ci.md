**What to build:** A passing change can publish an image and deploy the complete app from GitHub Actions through the homelab's Cloudflare Tunnel deploy path; failing core or browser journeys cannot become a release.

**Blocked by:** 11: Converge conflicting devices and explain losses; 12: Recover sync and preserve work through sign-out; 15: Inspect and amend a Day from Progress; 16: Delete a User's data deliberately; 17: Install and safely update the offline app; 19: Replicate, restore, and monitor history.

## Comments

**2026-10-20:** Corrected against `docs/deployment-home-server.md`: the original acceptance criteria said deployment goes "over Tailscale," copying ADR-0002's now-outdated text. The guide draws a hard line between the two SSH paths — `ssh.indraarianggi.xyz` behind Cloudflare Tunnel + Access is the machine/CI deploy path (forced-command, scoped to one `redeploy <project>` call), while Tailscale is reserved for the operator's own ad hoc admin access and is explicitly told not to be used for deploy. ADR-0002 has been updated to match; this ticket's secrets list and deploy-step description now follow §12.2/§12.3/§14.7 exactly.

**2026-10-20/21 (implementation):** Built `.github/workflows/deploy.yml` (`test` → `build` → `deploy` jobs) and `docs/release-and-deploy.md`. Confirmed the four deploy secrets from ticket 18 are already set (`gh secret list`) — no new secrets needed. One new operator config item this ticket adds: the `VITE_PRIVACY_CONTACT_EMAIL` GitHub repo **variable** (not a secret — it's public-facing, baked into `/privacy` at build time), which must be set once with `gh variable set VITE_PRIVACY_CONTACT_EMAIL --body "<real address>"` before the first push, or the `build` job's image build fails `vite.config.ts`'s own validation (fails loudly, doesn't ship a broken `/privacy`, but worth doing first to avoid a confusing first-run failure).

Verified locally, exactly mirroring what the `test` job runs (same env vars, same commands), before trusting the workflow: `pnpm run build` → `pnpm run typecheck` → `pnpm run smoke:browser` (dev mode) → `pnpm run smoke:browser` with `SMOKE_SERVER=production`. First full dev-mode run showed 3 failures, all in `breaks.test.ts`/`focus.test.ts` — debugged with the `systematic-debugging` skill rather than assumed-flaky: root cause was that the run straddled local midnight (23:58–00:02 WIB). Playwright's `page.clock` fakes time only inside the browser page, never the separate Node dev-server process; these three tests specifically re-sync to real wall time mid-test (`page.clock.setSystemTime(new Date())`) or force a server round-trip (`page.reload()`), and the app's day-bucketing (`localDay()` in `src/lib/task-contract.ts`) is a real local-calendar-date computation — so a run crossing midnight gets a client "today" and server "today" one calendar day apart. Confirmed by rerunning the same two files entirely after midnight: all 5 passed clean, no code changed. Not a regression, not caused by this ticket's changes, and not something to fix here — it's a pre-existing characteristic of those two tests that only bites an automated run that happens to straddle local midnight (dev-mode run: 112 passed/2 skipped; production-mode run: 113 passed/1 skipped, both exit 0).
