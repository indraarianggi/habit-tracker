# 19: Replicate, restore, and monitor history

**What to build:** The operator can recover Users' focus history after a node failure and learn when either the app or the off-site replica stops being healthy.

**Blocked by:** 18: Serve the app securely from the homelab.

**Status:** ready-for-human (app-level work done; operator steps in `docs/replication-and-restore.md` §1 and §3 pending)

- [ ] A Litestream sidecar (per ADR-0002) runs alongside the app container, continuously replicating the WAL-mode SQLite file to R2 or B2 with 30-day retention. This is additional to, not a replacement for, the host-wide nightly restic backup of `/opt/stack` that `docs/deployment-home-server.md` §9 already runs for every project on `fairy-vearth`.
- [x] Backups are not treated as immediately purged by account deletion — deleted Users' rows stay in both Litestream generations and restic snapshots until the 30-day window passes, matching the User-facing warning.
- [ ] Provide a reproducible restore procedure (`litestream restore` from the R2/B2 generation as primary, `restic restore` of the nightly `/opt/stack` snapshot as fallback), perform a pre-launch restore drill against representative Tasks, Check-ins, and settings, and specify quarterly repeats with a record of outcome.
- [ ] Register `https://habits.indraarianggi.xyz` with the external uptime monitor (§10) for "app stops responding." Add a separate heartbeat/age check for Litestream replication specifically — the generic restic heartbeat (§9) only covers the nightly host-wide backup, not this project's continuous replication — so a healthy-but-empty database is distinguishable from failed replication.
- [ ] A deliberate replica/restore smoke check compares recovered User history with the source and verifies the unhealthy replica-age signal fires correctly.

- `litestream.yml` (repo root) — sidecar config pinned to `litestream/litestream:0.5.17` (current release, verified via `gh api repos/benbjohnson/litestream/releases/latest` and confirmed present on Docker Hub for `linux/amd64`). Uses the real 0.5.x schema (singular `replica:`, not the older `replicas:` list a stale memory of Litestream might suggest), `snapshot.retention: 720h` (30 days) to match the User-facing "up to 30 days" backup warning already in `src/routes/today.tsx`/`privacy.tsx` — no app code changes were needed for the deletion/retention acceptance item, since it's satisfied purely by this config value plus the existing host-wide restic `--keep-monthly 6`, both already ≥30 days.
- `scripts/litestream/replication-heartbeat.sh` — a remote-aware staleness check, not just a liveness ping. Litestream 0.5.x does have a `heartbeat-url`/`heartbeat-interval` config option, but its docs site doesn't document whether that ping is conditioned on confirmed-successful remote uploads or just on the `replicate` process being alive — exactly the ambiguity this ticket's acceptance item warns about ("a healthy-but-empty database is distinguishable from failed replication"), so rather than depend on unverified semantics, the script instead calls `litestream ltx -json -level all` against the replica itself, takes the max remote LTX `timestamp`, and only pings healthchecks.io when that is fresher than `LITESTREAM_MAX_AGE_SECONDS` (default 600s) — a dead man's switch, same pattern as §9's existing restic heartbeat but measuring actual remote freshness instead of job completion.
- `scripts/litestream/restore-smoke-check.sh` — the acceptance item's smoke check: row-for-row compares one User's Tasks, Check-ins, and settings between a source and a restored database.
- `docs/replication-and-restore.md` — the project-specific runbook (deliberately a new file, not an edit to `docs/deployment-home-server.md`, which stays generic/host-wide per the earlier comment): bucket/credential setup, the compose.yaml sidecar snippet and systemd timer units for the operator to apply on the server (that compose.yaml isn't committed to this repo, same as ticket 18), the restore procedure (Litestream primary, restic fallback), the drill procedure, and a drill-outcomes log table.
